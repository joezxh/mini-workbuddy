## 三、技术选型小结

- **向量库**：PostgreSQL + pgvector（HNSW），无独立向量数据库
- **分割**：QA 对切片 + token 近似 chunker（wiki 侧无分块，整文单向量）
- **混合检索**：向量 + 中文 pg_trgm 子串 + RRF（k=60），wiki 与 KB 两套独立实现
- **SQL 安全**：sqlglot AST 白名单 + 只读 + 写申请一次性 token
- **连接器框架**：工厂注册 + 游标增量 + 白名单字段映射（无 eval）
- **前端**：antd v6 + tab 容器 + StateWrapper 统一加载态；Markdown 渲染均过 DOMPurify（安全面良好）

## 四、问题清单（按优先级）

### 阻断级
1. **版本 diff/回滚全链路断裂**：`version_service.py` 完整实现但无端点暴露；前端 `VersionDiffView.vue:20`/`VersionRollbackButton.vue:22` import 的 `diffArticle`/`rollbackArticle` 在 `api/wiki.ts` 中不存在（组件因 `VersionTimeline` 未接线而潜伏，启用即编译失败）
2. **connectors 后端不可用**：路由未注册 + import 不存在的模型类 + 同步假实现（启用即写 `status=success` 日志，数据失真）；且前端类型 notion/confluence/web/s3 与后端框架 http/dingtalk/feishu/wecom **两套类型体系完全对不上**
3. **`backend/app/routers/dataops/dataops.py:261` 缺 `select` import** → `GET /sources/{id}/tables` 运行时必 NameError 500
4. **ontology 与 wiki_admin 两个路由未注册**（wiki_admin 前缀声明与 registry 脱节）→ 管理后台 API 全 404
5. **`StandardManagement.vue:76-77` 编辑分支与新建分支调同一 create**，编辑永远变新建；删除未实现

### 功能缺陷
6. KB 子应用（`kb_router.py`）无认证，仅凭请求自带 `X-Tenant-Id` 隔离 → 水平越权；且自带 `get_db` 绕过主应用依赖注入
7. `BindingWorkbench` 待标注列从未赋值（死 UI）；`SqlWorkbench` dryRun、`DatasetManagement` 重建索引、`DocumentManagement` 重新上传、`ClassHierarchy` 校验均为前端假动作
8. wiki RAG 整文单向量无分块，超长文章检索精度差；RAG 索引用裸线程无队列/重试，重启丢任务
9. 无语雀连接器；无定时调度器消费 `sync_interval_min`（字段只是存值）
10. `ArticleEdit.vue:110-132` 用 `page_size=1000` 列表遍历找 slug，应补按 id 取详情端点

### 架构/质量
11. **wiki 文章 CRUD 两套并存**（`wiki.py` 内联 vs `article_service.py`），backlinks 行为不一致（只加不清 vs 修复版）；slugify 亦两份
12. N+1：`/ask` 循环回查文章（wiki.py L691-706）、scan_service 逐列 flush+add（L98-135）
13. 无分页：dataops sources/write-requests、sync-jobs 列表全量返回
14. 扫描在 HTTP 请求内同步执行（scan_service 自认无任务队列）；wiki 语义检索在 def 端点内同步 HTTP 调 embedding（失败要等满超时）
15. `search_service._log_search` 请求事务中途 commit（审计与业务事务不一致）；`wiki.py:256` 用 Pydantic v1 `body.dict()` 且 `exclude_none` 导致字段无法清空
16. 前端：大面积 `any`、`r.data || r || []` 归一化重复 15+ 处、4 个根面板模板逐字重复、"选择数据源"下拉重复 6 次、`index.vue` 780 行需拆分、`window.prompt` 输 token/新建类、死代码（`SearchBar.vue`、`VersionTimeline` 链、`types/wiki.ts` 多个类型、dataops/ontology/knowledgeBase API 未使用函数）

## 五、优化建议

### P0 — 修复断链（1~2 天）
1. **补版本管理 API**：在 `wiki.py` 加 `GET /articles/{id}/versions/{v}/diff` 与 `POST /articles/{id}/rollback`（复用现成 `version_service`），补齐 `api/wiki.ts` 两个函数，把 `VersionTimeline` 接进 `ArticleView` 版本抽屉
2. **修 dataops `select` import**（一行）
3. **`StandardManagement` 编辑走 update、删除接 DELETE 端点**（后端已有 PUT/DELETE `/standards` 外的 CRUD 基础，若缺则补）

### P1 — 打通外部集成（1 周量级）
4. **统一连接器类型体系**：以 `app/connectors/registry.py`（http/dingtalk/feishu/wecom）为准重写 `connector.py` 路由类型枚举与前端 `InstanceManagement` 硬编码；新建 `ConnectorInstance/ConnectorSyncLog` 模型（或改用现有 `meta_connector_ingest/sync_state`）并修 import
5. **接通真实同步**：`POST /{id}/sync` 调 `run_connector`（至少同步触发 + job 行记录真实状态），再加 APScheduler/celery-beat 消费 `sync_interval_min`；启用时不应预写 `success`
6. **补语雀连接器**（`OAuth2ApiConnector` 模式与钉钉一致，成本低）
7. **注册 wiki_admin / ontology 路由**，或删除前端对应面板避免"可点但 404"

### P2 — 一致性与安全
8. **收敛 wiki CRUD 到 `article_service.py`**（保留 backlinks 修复版），删除 `wiki.py` 内联重复逻辑；slugify 抽公共
9. KB 子应用并入主 app 依赖体系（认证 + 主 `get_db`），或至少加网关级鉴权
10. write_request 审批加"审批人≠申请人"校验；write-requests/sources/sync-jobs 补分页
11. `_log_search` 改为随主事务提交；`body.dict()` → Pydantic v2 `model_dump`，清空字段改显式 `exclude_unset`

### P3 — 体验与性能
12. **KB 检索 wiki 化**：`rag_ingestor` 引入 QaChunker/ApproxTokenChunker 分块 + `kb_segment` 复用（wiki 单向量仅作 fallback），`/ask` 结果批量查询消 N+1，并考虑 SSE 流式输出
13. **摄取任务加轮询**（processing 状态 3-5s interval 自动刷新）；SearchTester 加 loading；IngestionJobs.refresh 补 try/catch
14. **前端去重**：`r.data || r` 归一化下沉到 axios 拦截器；抽 `DataSourceSelect` 组件与 `useDataSources()` composable（6 处重复）；4 个根面板抽公共 `PanelTabs` 壳；消灭 `window.prompt`（token 改 modal + 密码框、新建类改表单）
15. **`index.vue` 拆分**为 CategoryTree / ArticleListTable / 独立 modal 组件，类型从 `types/wiki.ts` 落到组件
16. **元数据扫描异步化**：`job_runner.run_in_background` + 独立 Session（AGENTS.md 已有约定），前端加进度轮询
17. 删除死代码：`SearchBar.vue`、未接线组件链、`types/wiki.ts` 未用类型、各 API 层未用函数——或先接线再保留

---

**结论**：wiki 主链路（列表/编辑/查看/检索/问答）功能完整、安全处理规范，是最成熟的部分；通用知识库后端（pgvector 混检、sql_guard、Fernet）质量高但前端约半数操作是假实现；外部集成是唯一"前后端全断"的板块（类型体系分裂 + import 崩溃 + 假同步）。建议迭代顺序：先 P0 修复三处断链，再决定外部集成是"统一到现有 connectors 框架"还是砍掉前端等待后端，最后做 P2 的去重与安全收口。
