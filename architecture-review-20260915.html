① 配置巨石对象 (Config Monolith)

Strong
backend/app/config.py (383行)

⚡ 问题

单个 Settings 类承载 13 个关注点（数据库、Redis、JWT、CORS、搜索供应商×5、语音 RTC、Celery、审计、OpenTelemetry、SQLBot、DataOps 加密…）。任何模块的配置变更都要打开同一个文件；测试时无法只注入一组配置；不同部署环境的配置差异被扁平结构淹没。

✦ 方案

按领域拆分为独立配置协议：DatabaseSettings、RedisSettings、SearchSettings、VoiceSettings 等，由顶层 Settings 组合。每个协议可独立测试、独立 mock。

📈 收益

  • 杠杆：新增搜索供应商只需在 SearchSettings 加字段，不触碰数据库配置
  • 可测试性：单元测试可只注入 DatabaseSettings 的子集，无需构造完整 383 行对象

② 知识系统双轨并行 (Dual Knowledge Systems)

Strong
app/ai/knowledge/ (5文件) app/services/kb/ (8文件) app/ai/knowledge/pg_vector_store.py app/services/kb/pgvector_store.py

⚡ 问题

同一「知识库」概念被两个模块各自实现：ai/knowledge/ 有 pg_vector_store.py (193行)，services/kb/ 有 pgvector_store.py (400行)。两套向量存储、两套切片逻辑、两套检索入口。理解「知识库到底怎么工作」需要在两个目录间反复跳转。

✦ 方案

收敛为单一知识模块。保留 services/kb/ 的 HTTP 面（AgentScope 挂载点），将 ai/knowledge/ 的 RAG pipeline 和 OWL 引擎作为内部实现下沉到 services/kb/ 的依赖层。向量存储合并为一个 VectorStore 接口。

③ 前端上帝组件 (God Component)

Strong
frontend/src/views/admin/ai/skill/SkillManagement.vue (2316行)

⚡ 问题

单文件 2316 行，同时承载技能包管理、技能仓库浏览、脚本编辑、规则配置四个独立功能。模板、逻辑、样式高度耦合。任何子功能的修改都需要在这个巨型组件中定位上下文，AI 辅助编码时容易超出上下文窗口。

✦ 方案

按功能拆分为 4 个子组件 + 1 个容器组件：PackageList、HubBrowser、ScriptEditor、RuleConfig。共享状态通过 composable (useSkillManagement) 提取。容器组件只负责 Tab 切换和子组件编排。

④ 启动生命周期膨胀 (Lifespan Bloat)

Worth exploring
backend/app/main.py (lifespan: 170行)

⚡ 问题

lifespan() 函数承担了 5 种职责：表名迁移（ALTER TABLE）、建表（create_all）、kb 迁移、轻量列迁移（6 个 ALTER TABLE ADD COLUMN）、审计日志启动、工具管理初始化、OpenTelemetry 初始化。启动失败时难以定位是哪个阶段出错；迁移逻辑与建表逻辑交织，无法独立回滚。

✦ 方案

将启动阶段拆分为独立的初始化器接口 StartupPhase，每个阶段有 name、run()、rollback()。lifespan 只负责按序执行并记录耗时。迁移逻辑移入 alembic 或独立 migrations/ 脚本。

📈 收益

  • 局部性：每个启动阶段可独立测试（mock 数据库，验证阶段逻辑）
  • 杠杆：新增启动阶段只需添加一个 StartupPhase 实现，不触碰 lifespan 主体

⑤ DataOps 跨目录分裂 (Split DataOps)

Worth exploring
app/ai/dataops/ (10文件: connection, crypto, dialects, rule_engine) app/services/dataops/ (9文件: data_source_service, query_service, scan_service...)

⚡ 问题

DataOps 的基础设施（连接构造、加密、方言适配）在 ai/dataops/，业务服务（数据源管理、扫描、查询）在 services/dataops/。但 services/dataops/data_source_service.py 需要 import ai/dataops/crypto.py，形成跨目录的紧密耦合。两个目录的 rule_engine.py 各自独立（21行 vs 281行），命名相同但职责不同。

✦ 方案

合并为单一 dataops/ 模块。infrastructure/ 子包放连接、加密、方言；services/ 子包放业务服务。消除 ai/dataops/ 与 services/dataops/ 的人为边界。

📈 收益

  • 局部性：DataOps 的全部代码在一个目录树下，不再跨 ai/ 和 services/ 跳转
  • 杠杆：新增数据源类型只需在一个 dialects/ 目录下添加适配器

⑥ 仓储模式不一致 (Inconsistent Repository Pattern)

Worth exploring
app/repositories/ (仅4文件，只有 wiki/ 有仓储) app/services/ontology/ontology_repository.py (629行，放在 services/ 下)

⚡ 问题

仓储模式只在 wiki 和 ontology 使用，且 ontology 的仓储放在了 services/ 目录下而非 repositories/。其余模块（agent、ai、workflow）的 service 直接操作 ORM 模型。这导致数据访问逻辑的封装方式不一致：有时在 service 内，有时在独立仓储。

✦ 方案

两种选择：(A) 将 ontology_repository.py 移入 repositories/，统一仓储目录；(B) 承认当前混合模式，为复杂查询模块（ontology、agent_team）提供仓储，简单 CRUD 模块允许 service 直接操作 ORM。无论哪种，都需要在 CONTEXT.md 中记录决策。

📈 收益

  • 局部性：数据访问规则统一后，新增模块可以明确知道是否需要仓储
  • 可测试性：仓储作为接缝，可以 mock 数据库操作进行服务层单元测试

⑦ 语音模块归属模糊 (Voice Module Placement)

Speculative
app/duplex/voice/ (58文件) app/routers/admin_voice_config.py (在 routers/ 根目录) app/models/duplex/ (3文件) app/schemas/duplex/ (1文件)

⚡ 问题

语音 RTC 模块使用 duplex 作为顶级目录名，但其本质是「调解语音」业务领域。duplex 这个名字暗示技术实现（全双工），而非业务语义。且路由文件 admin_voice_config.py 放在 routers/ 根目录而非 routers/duplex/ 或 routers/voice/，与其他模块的组织方式不一致。

✦ 方案

将 duplex/ 重命名为 mediation/voice/（与业务域对齐），并将 routers/admin_voice_config.py 移入 routers/mediation/ 子目录。这是低优先级改动，可在下次大改时顺带进行。

📈 收益

  • 局部性：目录名反映业务语义，新人可快速理解模块归属
  • 杠杆：未来若增加其他调解渠道（如视频），可在 mediation/ 下自然扩展

🏆 首选推荐

① 配置巨石对象 — 优先处理

这是投入产出比最高的改动。原因：

  1. 零运行时风险：纯重构，不改变任何外部行为，只是将 Settings 的字段分组到子协议中
  2. 影响面可控：只需修改 config.py 和引用 settings.XXX 的地方（通过 property 代理可保持向后兼容）
  3. 解锁后续改进：配置分组后，搜索模块、语音模块的配置可以独立测试，为后续模块合并（候选②⑤）铺路
  4. 立竿见影：任何开发者打开 config.py 时，不再被 383 行的扁平结构淹没

建议工作量：2-3 小时，可在单个 PR 中完成。
